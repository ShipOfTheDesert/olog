## Requirements Coverage

- **FR1 (No suspension on a dead worker)** — **Satisfied.** `flush` and `shutdown` both return promptly after the worker has terminated (switch cancellation). The `flush` path uses `Fiber.first` with the `stopped` promise; `shutdown` awaits `stopped`. The tests `test_flush_returns_after_switch_cancellation` and `test_shutdown_returns_after_switch_cancellation` verify this.

- **FR2 (Concurrent-safe, idempotent shutdown)** — **Partially satisfied.** The CAS-based state machine, `stopped` promise, and mutex-coordinated producers make shutdown safe under fiber-level concurrency. However, the implementation is **not safe when `shutdown` (or `log`) is called from multiple domains**, because it uses `Eio.Mutex` and `Eio.Stream`, which are documented as fiber-safe but not domain-safe. The PRD explicitly requires “any number of fibers or domains”. The test `test_concurrent_shutdown_all_callers_return` uses a second domain, but the underlying primitives are not guaranteed to be safe in that scenario.

- **FR3 (Sink failures as values; cancellation never swallowed)** — **Satisfied.** The sink contract is changed to `(unit, string) result`. `run_sink_op` handles `Ok`/`Error`, always re-raises `Eio.Cancel.Cancelled`, and tolerates raising sinks via a narrow handler. `Output.protect` is deleted; the exception→result conversion is at the `Output.make` boundary. Tests `test_sink_emit_error_does_not_stop_worker`, `test_contract_violating_sink_does_not_stop_worker`, and `test_output_write_returns_error_on_io_failure` cover the main paths.

- **FR4 (Configuration validated at creation)** — **Satisfied.** `Config.make` rejects `queue_depth < 1` with `Error`. `Config.t` is private; `Config.default` is removed. `test_config_make_rejects_nonpositive_queue_depth` verifies.

- **FR5 (Every accepted entry is accounted for)** — **Partially satisfied.** The producer mutex and the `enqueue_or_drop` logic ensure conservation under fiber concurrency. The cancellation drain sets `Stopped` under the mutex before draining, which prevents lost entries. The defensive post-`Shutdown` drain counts stragglers as drops. The tests `test_conservation_under_concurrent_load` and `test_conservation_after_cancellation` verify the invariant.  
  **However**, the implementation does **not** drain the queue in the worker’s `finally` on an unexpected exception. If the worker loop raises an exception (not cancellation), the `finally` only closes sinks and resolves `stopped`; remaining queue entries are silently lost without incrementing `drop_count`. This violates the requirement that **no code path** discards an entry without counting it.

- **FR6 (Configurable timestamp-failure policy)** — **Satisfied.** `Fail` mode probes the clock at `create` and returns `Error` if unrepresentable; residual failures fall back to the `Mark_invalid` behaviour (epoch + `olog.invalid_timestamp` marker). Tests cover both modes.

- **NFR1 (Non-blocking guarantee preserved)** — **Satisfied.** `log`/`log_exn` never suspend waiting for queue space; they drop and count.

- **NFR2 (Contracts protected by tests)** — **Satisfied** for the tested paths. The new lifecycle, conservation, and timestamp tests are present. The domain-safety gap and the missing drain-on-unexpected-exception are not covered.

- **NFR3 (No new runtime dependencies)** — **Satisfied.**

- **NFR4 (Land before any tagged release)** — **Satisfied** (the breaking sink contract change is pre-1.0).

## Design Divergence

1. **Domain-unsafe primitives (critical divergence).**  
   The RFC’s state-machine design assumes a mutex that serialises producers and a queue that can be safely used across domains. The implementation uses `Eio.Mutex` and `Eio.Stream`, both of which are documented as **not domain-safe**. The PRD explicitly requires shutdown to be safe “from any number of fibers or domains” (FR2). The tests that use `Eio.Domain_manager` (e.g., `test_concurrent_shutdown_all_callers_return`, conservation tests) exercise paths that are not guaranteed to work.  
   *Verdict:* **Wrong – code must change.** The logger must use domain-safe synchronisation (e.g., `Stdlib.Mutex` and a domain-safe queue, or an atomic-based lock-free queue) or the multi-domain requirement must be explicitly relaxed. The current implementation should not ship with a claim of domain safety.

2. **Unexpected worker exception path not draining the queue.**  
   The RFC’s design relies on the worker’s `finally` to resolve `stopped` on every exit path, but the `finally` does **not** drain the queue. The PRD FR5 requires that **every accepted entry** is either emitted or counted as dropped, with no silent loss. A worker crash leaves entries in the queue uncounted.  
   *Verdict:* **Wrong – code should change.** The `finally` block should drain remaining entries and count them as drops (or emit them, if possible) to satisfy the conservation guarantee.

## Correctness Concerns

1. **[Critical] Domain-unsafe primitives.**  
   `logger.ml` uses `Eio.Mutex` and `Eio.Stream` for the producer mutex and the message queue. These are accessed from multiple domains in the tests (and any real-world multi-domain use). The Eio documentation states they are not domain-safe. This can lead to data races, deadlocks, or undefined behaviour.  
   *Fix:* Replace with domain-safe mechanisms, or restrict the API to single-domain use only (and update the PRD accordingly).

2. **[High] Accounting violation on unexpected worker exception.**  
   `worker_loop`’s `finally` (logger.ml line ~188) does not drain the queue. If the worker’s `loop` raises an exception, any queued entries are silently lost. This breaks the “submitted = emitted + dropped” conservation invariant.  
   *Fix:* Drain the queue in `finally` and count remaining entries as drops, or ensure the worker cannot raise unexpected exceptions.

3. **[Medium] `shutdown` Shutdown-message enqueue outside the mutex.**  
   The `Shutdown` message is added to the queue after releasing the mutex (`logger.ml` line ~265). The rationale is to avoid holding the lock during a potentially blocking `add`. This is safe in practice because the drain loop handles it, but it introduces a subtlety: the `Shutdown` message could be added after the worker’s cancellation drain has already set `Stopped` and started draining. The drain will see the `Shutdown` and ignore it, which is harmless. However, the documentation’s claim that “the single Shutdown is therefore guaranteed to be the last message the worker sees” is not strictly true if the worker is in the cancellation drain; it may see the `Shutdown` but it is not the last message processed. The invariant that no `Log` follows `Shutdown` still holds. The design is acceptable but the comment is slightly misleading.

4. **[Low] `flush` may block on `Eio.Stream.add` if worker dies unexpectedly without draining.**  
   If the worker dies due to an unexpected exception and the queue is not drained (see concern 2), the `flush` function’s `add` could block forever. However, the `stopped` promise would be resolved, so `Fiber.first` would eventually return via the `stopped` branch. The `add` would remain blocked, leaking a fiber. This is a resource leak. Fixing concern 2 resolves this.

## Test Adequacy

- The tests for the new lifecycle, conservation, and timestamp policies are present and correctly structured. The `with_timeout` helper effectively turns hangs into test failures.
- **Missing coverage:**  
  - No test exercises the worker’s unexpected-exception path to verify that the accounting invariant holds.  
  - The conservation tests use multiple domains, but the domain-unsafe primitives make these tests unreliable; they may pass by accident on some runtimes but do not prove correctness.  
  - The test `test_concurrent_shutdown_all_callers_return` uses a second domain, but the underlying mutex/stream are not domain-safe, so the test is not a valid validation of the multi-domain requirement.

## Second Opinion Differs

1. **The implementer appears to have assumed `Eio.Mutex` and `Eio.Stream` are domain-safe,** given the PRD’s requirement for domains and the RFC’s discussion of “multi-domain contention” (R1). The Eio documentation explicitly disclaims domain safety. This is a fundamental mismatch that an outside reviewer would question: the design was built on an assumption that the chosen primitives are up to the task, but they are not.

2. **The `finally` block was designed to resolve `stopped` and close sinks, but not to drain the queue.** The implementer may have reasoned that the worker only exits via `Shutdown` (which drains) or cancellation (which drains), so the queue is always empty when `finally` runs. The PRD’s FR5 is absolute: “no code path may discard an entry without incrementing the counter.” An unexpected exception is a code path that is reachable (a bug in the worker, a sink that raises an unexpected exception despite the result contract, etc.) and would cause silent loss. The implementation should be robust against this.

3. **The `shutdown` function adds the `Shutdown` message outside the mutex** to avoid a potential deadlock with the cancellation drain. The comment suggests this is intentional and safe. While it is safe in practice, a reviewer might question whether the invariant “Shutdown is the last message” is necessary. The drain-on-cancel path already handles the case where `Shutdown` arrives during drain, so the invariant is not strictly required. The code is correct, but the comment slightly overstates the guarantee.

## Orchestrator triage (post-review, 2026-06-14)

Each finding was verified against `lib/logger.ml` and the **installed Eio 1.3**
interface/implementation before acting.

**Finding 1 (Critical: "Eio.Mutex/Stream are domain-unsafe") — REJECTED, false
premise.** The review's claim that Eio "explicitly disclaims domain safety" is
incorrect:

- `Eio.Stream` — `stream.mli` (Eio 1.3), verbatim: *"Streams are thread-safe and
  so can be shared between domains and used to communicate between them."*
  `take_nonblocking` even documents the "another domain may add" case.
- `Eio.Mutex` — `eio_mutex.ml` (Eio 1.3): `type t` holds `mutex : Mutex.t` (a
  `Stdlib.Mutex`) and its `state`/`waiters` are *"Owned by `t.mutex`"*; every op
  takes `Mutex.lock t.mutex`. Domain-safe **by construction**. The `.mli`'s only
  domain note is that mutexes are *unnecessary* within a single domain — i.e.
  cross-domain/blocking critical sections are their reason to exist.

So the `Domain_manager`-driven conservation and concurrent-shutdown tests are
valid (not racy), and FR2 is met. The suggested remedy (swap to `Stdlib.Mutex`
+ a hand-rolled queue) is RFC 0013 Option C, explicitly rejected as higher
concurrency-bug risk for zero gain — adopting it would regress correct code on a
bad premise. No code change; the verified reliance is now noted at the `mutex`
field in `logger.ml`.

**Finding 2 (High: `finally` doesn't drain) — accurate observation, severity
overstated → HARDENED.** Factually correct that `finally` did not drain. But
`run_sink_op` catches every non-`Cancelled` exception and `Stream.take` raises
only `Cancelled`, so there is **no currently-reachable non-`Cancelled`
exception path out of `loop ()`** — this was defense-in-depth, not a live FR5
break. Hardened anyway (cheap, unconditional FR5): `finally` now runs
`stop_and_count_drain` — set `Stopped` under the producer mutex, then
`take_nonblocking`-drain counting any straggler `Log` as a drop. No-op on the
normal/cancel paths (queue already empty).

**Finding 3 (Medium: "Shutdown is the last message" comment) — comment fixed.**
The `shutdown` comment now states the real invariant (no `Log` can follow
`Shutdown`; a racing `Flush` may, harmlessly) instead of "Shutdown is the last
message." Code was already correct.

**Finding 4 (Low: flush block/leak) — closed by the Finding 2 hardening;** no
separate change (RFC R4 already documents the harmless resolver leak).
